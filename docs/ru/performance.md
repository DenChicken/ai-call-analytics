# Производительность

Документ о том, как выбрать режим работы и что делать, если обработка идет
медленно.

## Главный выбор: видеокарта или процессор

Обработка состоит из двух тяжелых шагов: распознавание речи и анализ текста.
Оба можно выполнять либо на обычном процессоре, либо на видеокарте NVIDIA.

Разница по скорости велика - видеокарта обрабатывает разговоры в несколько раз
быстрее. Порядок величин такой:

| Режим | Обработка одного разговора |
|---|---|
| Только процессор | Несколько минут |
| Видеокарта | Меньше минуты |

Точные цифры зависят от оборудования, длительности разговора и выбранных
моделей.

**Когда хватит процессора.** Если звонков немного - скажем, до сотни в день, - и
результаты нужны не сразу, система справится и без видеокарты. Очередь будет
разбираться постепенно.

**Когда нужна видеокарта.** Если звонков сотни в день, на процессоре система
перестанет успевать: очередь будет расти быстрее, чем разбираться.

Проверить, справляется ли система, просто: посмотрите на дашборде показатель
"В очереди". Если он день ото дня растет - не успевает.

## Как включить видеокарту

Отдельной команды для этого нет - режим задается в настройках обработчика, файл
`configs/pipeline/config.toml`. Система сама поймет, что нужна видеокарта.

Измените два параметра:

```toml
[asr]
device = "cuda"

[llm]
gpu_layers = "all"
```

Затем перезапустите:

```
python deploy.py restart pipeline
```

Обратный переход - вернуть `device = "cpu"` и `gpu_layers = "none"`.

Перед включением на сервере должны быть установлены драйвер NVIDIA и средства
работы с видеокартой из контейнеров - см. [Установка](installation.md).

## Если видеокарта слабая

Параметр `gpu_layers` не обязательно ставить в `all`. Можно указать число - тогда
часть работы уйдет на видеокарту, а часть останется процессору:

```toml
gpu_layers = 20
```

Это помогает, когда модель целиком не помещается в память видеокарты. Подбирается
опытным путем: увеличивайте, пока система работает устойчиво.

Признак того, что памяти не хватает, - обработчик перезапускается, а в журнале
встречаются сообщения о нехватке памяти.

## Две модели в одной памяти

Распознавание речи и анализ - это две разные модели, и обе занимают память.
Работают они по очереди, но по умолчанию обе остаются загруженными - так быстрее.

Если памяти не хватает, включите выгрузку:

```toml
[asr]
unload_after = true

[llm]
unload_after = true
```

Тогда модель будет освобождать память после работы. Обработка станет медленнее -
каждый раз модель приходится загружать заново, - но система сможет работать там,
где иначе не помещается.

Достаточно включить выгрузку для одной из двух моделей - обычно этого хватает.

## Длина разговора

Параметр `context_tokens` определяет, насколько длинный разговор помещается в
анализ. По умолчанию 8192 - этого хватает примерно на 30-40 минут разговора.

Если встречается ошибка "Разговор не помещается в контекст модели", есть два
пути:

- увеличить `context_tokens` - потребует больше памяти;
- ограничить длительность звонков в настройках загрузчика параметром
  `max_call_duration_seconds`.

Второй путь часто разумнее: очень длинные разговоры обычно нетипичны, и оценивать
их по общим критериям все равно некорректно.

## Настройка под процессор

Если работаете без видеокарты, укажите, сколько ядер отдать под анализ:

```toml
[llm]
threads = 8
```

Разумное значение - число физических ядер процессора. Ставить больше
бессмысленно, обработка от этого не ускорится.

## Выбор модели

В поставке используются модели среднего размера - разумный баланс качества и
скорости. Их можно заменить, указав другие в параметрах `repo_id` и `model_file`.

Правило простое: модель побольше оценивает точнее, но работает медленнее и
требует больше памяти.

После смены модели ее нужно скачать - автоматически это не произойдет. Команду
для скачивания печатает `python deploy.py init`, ее же можно выполнить вручную
(см. [Установка](installation.md)).

Если выбранная модель не подойдет по формату, обработчик сообщит об этом при
запуске.

## Место на диске

| Что | Сколько |
|---|---|
| Модели | Несколько гигабайт, единовременно |
| Записи разговоров | Около 1 МБ на минуту, постоянно растет |
| База данных | Десятки мегабайт в год |

Основной рост дают записи разговоров. Как их чистить - в разделе
[Эксплуатация](operations.md).

## Что делать, если очередь растет

По порядку:

1. Убедитесь, что обработчик работает: `docker compose ps`.
2. Посмотрите его журнал: `python deploy.py logs pipeline`.
3. Если система на процессоре - рассмотрите видеокарту, это даст наибольший
   выигрыш.
4. Отсейте лишние звонки: поднимите `min_call_duration_seconds`, чтобы не
   тратить время на короткие разговоры.
5. Уменьшите `context_tokens`, если разговоры короткие - анализ пойдет быстрее.

Если очередь выросла разово - например, после первого запуска с большим
`initial_lookback_days` - это нормально. Система разберет ее и вернется к обычному
режиму.
