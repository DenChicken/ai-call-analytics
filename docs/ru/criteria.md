# Критерии оценки

Это главная настройка системы. Здесь вы определяете, за что менеджеры получают
баллы. Все остальные параметры влияют на скорость и удобство, а этот - на смысл
результата.

Файлы лежат в папке `configs/pipeline`:

- `criteria.toml` - критерии оценки;
- `types.toml` - типы разговоров.

## Критерии

Критерий - это одно проверяемое действие менеджера. Система читает расшифровку
разговора и по каждому критерию решает: выполнен или нет. Промежуточных оценок
нет.

Выглядит критерий так:

```toml
[[criterion]]
code = "contact_initiation"
label = "Контакт и начало разговора"
description = "Менеджер поздоровался, назвал компанию и свое имя."
```

- `code` - служебное имя, латиницей без пробелов. Пользователь его не видит.
  Именно по нему система узнает критерий, поэтому менять его у существующего
  критерия не следует.
- `label` - название, как оно будет выглядеть в отчетах. Пишите коротко: длинные
  названия плохо помещаются на графиках.
- `description` - описание для системы. Это самая важная строка.

## Как писать описание

По описанию система решает, засчитать критерий или нет. От его точности зависит
качество оценки.

Описывайте наблюдаемое действие - то, что можно услышать в разговоре.

Хорошо:

```
Менеджер спрашивает про город, бюджет, сферу бизнеса или параметры клиента.
```

Плохо:

```
Менеджер хорошо работает с клиентом.
```

Второе описание нельзя проверить: непонятно, что именно должно прозвучать.

Несколько правил:

- Одно описание - одно действие. Если получается "и то, и другое" - разделите на
  два критерия.
- Перечисляйте варианты через "или": так система поймет, что засчитывать.
- Избегайте оценочных слов: "качественно", "правильно", "профессионально".
- Пишите в третьем лице, как в примерах.

## Сколько критериев делать

Разумный диапазон - от 8 до 15.

Меньше 5 - оценка получается грубой, менеджеров сложно сравнивать. Больше 20 -
разговор физически не может содержать столько действий, и у всех будут низкие
баллы.

В поставке 12 критериев. Их удобно взять за основу и переписать под себя.

## Как менять критерии

Файл можно править в любой момент. Изменения применяются при следующем запуске
обработчика:

```
python deploy.py restart pipeline
```

**Что происходит с уже оцененными разговорами.** Ничего. Старые оценки остаются
как есть - система не пересчитывает прошлые разговоры задним числом.

**Если добавить критерий.** Он начнет применяться к новым разговорам. У старых
по нему оценки не будет.

**Если удалить критерий.** Он перестанет применяться к новым разговорам. Ранее
выставленные по нему оценки сохранятся и останутся видны в карточках старых
разговоров с пометкой "отключен".

**Если изменить название или описание.** Применится к новым разговорам. Учтите,
что после изменения описания оценки до и после правки становятся не вполне
сравнимы - критерий стал означать другое.

Из этого следует практическое правило: **менять критерии лучше редко и осознанно,
предпочтительно на границе периода** - месяца или квартала. Иначе графики
изменений будет трудно читать.

Удалять критерий из файла безопасно - данные не пропадут.

## Типы разговоров

Файл `types.toml` устроен так же:

```toml
[[type]]
code = "sales"
label = "Продажа"
description = "Разговор менеджера с клиентом. Обсуждение товара, покупки, цены, сроков."

[[type]]
code = "not_sales"
label = "Другое"
description = "Автоответчик, пустой или отвлеченный разговор."
```

Система относит каждый разговор ровно к одному типу. Это нужно, чтобы отделить
настоящие продажи от служебных звонков и автоответчиков - иначе они испортят
статистику.

Описание типа так же важно, как описание критерия: именно по нему система решает,
к какому типу отнести разговор. Пишите его по тем же правилам - через наблюдаемые
признаки, а не оценочными словами. Чем больше у вас типов, тем важнее, чтобы их
описания явно отличались друг от друга.

Обязательно оставьте один тип для всего постороннего. Иначе система будет
вынуждена относить автоответчики к продажам.

Двух типов обычно достаточно. Если разговоры бывают разные - например, продажи и
поддержка - можно добавить третий.

В веб-интерфейсе по типам можно фильтровать: посмотреть статистику только по
продажам, исключив прочее.

## Указания для модели

В папке `configs/pipeline/prompts` лежат два файла - это инструкция, по которой
работает языковая модель. Обычно их менять не нужно: критериев и типов
достаточно, чтобы настроить систему под себя.

Если вы все же правите эти файлы, помните:

- В файле `user.txt` есть отметки `{criteria}`, `{types}`, `{manager}` и
  `{transcript}` - на их место подставляются данные разговора. Все четыре должны
  остаться, иначе система не запустится.
- Рядом, в файле `config.toml`, есть параметр `label` в разделе `[prompt]`. Это
  пометка версии, она сохраняется вместе с каждым результатом. Меняя инструкцию,
  меняйте и пометку - тогда в карточке разговора будет видно, по какой версии он
  оценивался.

## Проверка

После изменения критериев проверьте результат:

1. Перезапустите обработчик.
2. Дождитесь обработки нескольких новых разговоров.
3. Откройте карточку разговора и послушайте запись, сверяя с оценками.

Если система засчитывает критерий там, где его нет, - описание слишком широкое.
Если не засчитывает очевидное - слишком узкое или требует сразу нескольких
условий.

Ошибки в файле система обнаружит при запуске и сообщит о них - смотрите
[Решение проблем](troubleshooting.md).
